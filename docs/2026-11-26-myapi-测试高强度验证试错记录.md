# myapi 高强度验证试错记录（2026-11-26）

> 背景：用户让我"继续测内部调度""写多点测试""各种多轮对话日志全部对齐""继续高强度验证"。这一轮往 `gateway.rs` / `main.rs` / `gateway_logs.rs` 补了 24 个测试（174 → 198），中间踩了 5 个坑，其中 2 个是真 bug（并发日志丢失、失败日志记别名）。这篇把"为什么不行"原原本本记下来。

---

## 坑 1：responses 多轮测试，上游只收到 3 条不是 4 条

**现象**：新写的 `responses_endpoint_multi_turn_history` 断言"上游 messages 长度 3"失败，实际收到的是别的数。

**排查**：去翻 `protocol.rs` 的 `responses_to_chat` → `append_responses_item`。发现 `input` 数组里每个 `{"type":"message",...}` 会转成一条 chat 消息，**但** `instructions` 字段（responses 协议的系统提示）会先被塞成一条 `system` 消息：

```rust
// responses_to_chat 里
if let Some(ins) = body.get("instructions") {
    let text = instruction_text(ins);
    if !text.is_empty() {
        messages.push(json!({"role": "system", "content": text}));
    }
}
```

我测试的 payload 带了 `"instructions": "you are helper"`，所以上游实际收到 `system + user/assistant/user = 4 条`，不是 3 条。

**修复**：断言改成 4 条，并补了位置断言（`messages[1]=第一轮`、`messages[2]=assistant` 保留、`messages[3]=第二轮`）。

**教训**：responses 协议的 `input` 数组**不含 system**，`instructions` 是独立的顶层字段，转换时会提前变成 `system` 消息。写跨协议多轮测试时，先想清楚转换矩阵会把哪些字段提前塞进 messages。

## 坑 2：failover 日志测试，响应不是 200

**现象**：`logs_failover_records_upstream_status` 断言"failover 后应 200"失败。明明配了两个通道（ch1 恒 500、ch2 恒 200），上游也 mock 了。

**排查**：一开始 payload 用的是 `"model": "up-bad"`（只匹配 ch1 的模型名）。`select_channel` 按**请求模型名**找候选，`up-bad` 只命中 ch1（ch1 的模型是 `up-bad`），ch2 的模型是 `up-good`，不匹配——所以 failover 根本没有第二候选，ch1 500 重试耗尽就透传了。这也解释了为什么已有的 `upstream_5xx_fails_over_to_next_channel` 能过：它的 payload 用 `my-model`，而 ch1/ch2 都配了 `alias: my-model`。

**修复**：把两个通道的模型都加 `"alias": "my-model"`，payload 改 `"model": "my-model"`，这样两个候选都命中，ch1 500 → ch2 200。

**教训**：failover 测试要测的是"候选链切换"，**payload 的模型名必须匹配到两个通道**（用共同 alias），不能只匹配失败通道。只匹配失败通道 = 没有第二候选，failover 根本不会发生。

---

## 坑 3：失败日志记的是档位别名，不是真实上游模型名（真 bug）

**现象**：修好坑 2 后，日志断言又失败。打印实际行：

```
DIAG rows: [("my-model", 500), ("up-good", 200)]
```

ch1 失败那行的 `model` 是 `my-model`（请求别名），不是 `up-bad`（真实上游模型名）。

**排查**：`gateway.rs` 里失败路径的 3 处 `log_request` 都是：

```rust
model: requested_model.into(),
```

而成功路径（约 1812 行）用的是 `model: selected.upstream_model.clone()`。也就是说：**成功日志记真实上游名，失败日志记请求名**，两者不一致——用户在日志里根本看不出失败请求实际打到了哪个上游模型。

**修复**：失败路径 3 处 `requested_model.into()` 全部改成 `selected.upstream_model.clone()`（`forward_one` 里 `selected` 就在作用域内）。

**教训**：这正验证了用户说的"日志全部要对齐"。成功/失败日志的 `model` 字段语义必须一致，都记真实上游模型名。以后新增日志路径，对照成功路径的字段来源，别想当然。

## 坑 4：流式 usage 测试偶发 flaky（单独跑必过、全量偶发）

**现象**：`stream_mock_openai_usage_recorded` / `stream_mock_gemini_usage_recorded` 在全量 `cargo test` 里偶尔失败，单独跑必过。断言是"Gemini 流式 input"这类 usage 值。

**排查**：测试先 `collect` 完 SSE body，再 `sleep 250ms` 后查 `query_summary`。流式 usage 是 SSE 处理完后**异步写日志**的（`log_request` 是 `spawn_blocking`），250ms 固定 sleep 在机器负载高（全量并行）时不够，usage 还没入库就断言了。

**修复**：写了个 `wait_summary` helper，轮询等 usage 入库（最多 3 秒，100ms 一查），替换掉 3 个流式 + 1 个非流式测试里的固定 sleep。

```rust
async fn wait_summary(root: &Path, expect_in: Option<i64>, expect_out: Option<i64>) -> bool {
    for _ in 0..30 {
        tokio::time::sleep(Duration::from_millis(100)).await;
        let s = gateway_logs::query_summary(root).unwrap();
        // ...检查 input/output 达到期望就 true
    }
    false
}
```

**教训**：凡断言"异步写日志的结果"，不要用固定 sleep，要用**轮询等待**。固定 sleep 是 flaky 的温床，负载一变就崩。

## 坑 5：并发日志丢失——SQLite 单写锁（真 bug，最严重）

**现象**：`concurrent_50_requests_all_ok` 断言"50 并发应记 50 条日志"失败，实际只记了 20 条。后面加到 100 并发时更明显（丢更多）。但**单请求测试全过**、这个并发测试**单独跑也过**，只在**全量并行**时丢。

**排查**：`gateway_logs::log_request` 每次调用都 `Connection::open` 开新连接然后 `INSERT`，**没有 busy_timeout、没有 WAL、没有重试**。50 个并发请求同时 `INSERT`，SQLite 单写锁冲突，拿不到锁的连接直接 `Err`，只 `eprintln` 一行就丢了——所以响应全 200（转发成功），但日志缺。

关键点是：**单独跑**时机器空闲、写入够快，全量并行时负载高、写锁冲突被放大，才暴露。

**修复**（三步）：
1. `ensure_ready` 里加 `PRAGMA journal_mode=WAL;`（并发读写分离）；
2. `log_request` 加 `busy_timeout(5s)`；
3. `INSERT` 失败重试 5 次（每次 sleep 50ms）兜底。

```rust
let _ = conn.busy_timeout(std::time::Duration::from_secs(5));
let _ = conn.execute_batch("PRAGMA journal_mode=WAL;");
// ...INSERT 失败重试 5 次...
```

**教训**：SQLite 并发写不处理锁 = 静默丢数据。转发路径成功但日志缺失是最坑的——用户以为记上了，其实没有。凡是"高并发 + SQLite 写"，WAL + busy_timeout + 重试是标配。**单请求测试全过不代表并发安全**，一定要有并发压力测试才能暴露。

---

## 小结

| 坑 | 类型 | 根因 | 修复 |
|----|------|------|------|
| responses 多轮 3vs4 | 测试断言错 | `instructions` 提前变 `system` 消息 | 断言 4 条 + 位置断言 |
| failover 非 200 | 测试场景错 | payload 只匹配失败通道，无第二候选 | 共用 `alias: my-model` |
| 失败日志记别名 | **真 bug** | 失败路径用 `requested_model`，成功用 `upstream_model` | 统一 `selected.upstream_model` |
| 流式 usage flaky | 测试时序 | 固定 sleep 250ms 不够 | `wait_summary` 轮询 |
| 并发日志丢失 | **真 bug** | SQLite 单写锁无 busy_timeout/WAL/重试 | WAL + busy_timeout + INSERT 重试 |

两个真 bug（失败日志别名、并发日志丢失）都是用户要求的"日志全部对齐"和"高强度验证"逼出来的——单请求、单路径测试根本发现不了。
