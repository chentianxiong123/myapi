# 性能对比：Rust 版 vs Python 版

> 同一台机器、同一个 mock CPA、同一份配置，多轮取中位数。
> 复现：`python scripts/bench.py`（路径全部参数化，不写死个人目录）

## 测试环境

| 项 | 值 |
|---|---|
| 机器 | Windows 11 |
| Python | 3.14 |
| Rust | stable-x86_64-pc-windows-gnu |
| Rust 构建 | `--release`（`opt-level=z` + `lto` + `codegen-units=1` + `panic=abort`）|
| CPA 后端 | 本机 mock（127.0.0.1:18317，6 个模型）|
| 轮次 | CLI 5 轮取中位，HTTP 40 次取中位/P95 |

## 结果

| 维度 | Rust release | Python 3.14 | 倍数 |
|---|---|---|---|
| 二进制体积 | **3.59 MB** | —（需 CPython + pyyaml + requests）| — |
| 冷启动到端口可用 | 339.7 ms | 328.6 ms | ~1.0x |
| 空闲工作集 | **5.8 MB** | 29.9 MB | **5.2x** |
| 忙时工作集 | **6.0 MB** | 30.8 MB | **5.1x** |
| CLI `check` 中位 | **18.2 ms** | 259.2 ms | **14.2x** |
| HTTP 请求中位 | **0.67 ms** | 2.66 ms | **4.0x** |
| HTTP 请求 P95 | 16.12 ms | 25.29 ms | 1.6x |
| HTTP 请求 max | 29.3 ms | 29.1 ms | 1.0x |

### Python 那 30MB 花在哪了

```
纯解释器          13.25 MB
+yaml/requests    +19.2  MB    ← 大头在这
+本项目模块         +0.2  MB
```

应用代码本身几乎不占内存，**底噪全部来自运行时和第三方依赖**。
Rust 的 5.8MB 里含全部功能、静态链接的 sqlite。

### debug vs release（Rust 内部对比）

| | debug | release | 收益 |
|---|---|---|---|
| 体积 | 111.9 MB | 3.59 MB | 31x |
| CLI check | 30.7 ms | 18.2 ms | 1.7x |
| 工作集 | 9.2 MB | 5.8 MB | 1.6x |

## 三个值得记的结论

**1. 冷启动居然持平（~330ms），瓶颈不在语言运行时。**
卡在 OS 端口绑定和首次 CPA 连接探测上，不是解释器加载。真正拉开差距的是**重复执行的命令**——CLI 差 14.2 倍，因为 Python 每次都要重新 import 那 19MB 依赖。

**2. 常驻服务看工作集，一次性命令看 CLI 耗时。**
面板是常驻的，5.2x 的内存差就是长期收益；CLI 14.2x 主要吃的是依赖加载，不是业务逻辑本身更快。

**3. 尾部延迟更值钱的指标是 P95，不是中位。**
中位 4x，但 P95 只有 1.6x。Python 的单线程 GIL + 调度在压力下尾部抖动更大，max 却持平（都被网络 IO 兜底了）。

## 复现方法

```bash
# 全自动探测（找 target/<profile>/myapi，找项目根 web/app.py）
python scripts/bench.py

# 指定构建类型和路径
python scripts/bench.py --profile debug \
    --rust ./target/debug/myapi.exe \
    --py-src /path/to/python-src \
    --config config/myapi-config.yaml

# 只测 CLI，不起 web（更快，适合 CI）
python scripts/bench.py --no-web --cli-rounds 10
```

完整结果落在 `target/bench-result.json`。

### 已知的测量注意事项

- **不要用 32 位 `GetProcessMemoryInfo` 采样 64 位进程**，返回值会错得离谱（83KB / 114KB 这种量级）。Windows 上走 `Get-Process.WorkingSet64`，Linux 走 `/proc/<pid>/status` 的 `VmRSS`。
- **tar 解包要防 `__pycache__`**：tar 保留 mtime，旧 `.pyc` 可能比新源码"新"，Python 直接用旧字节码，表现为"改了代码没生效"。
- **PowerShell 重定向会被文件锁挡住**：目标文件正被读时写不进去，旧内容留着，表现为"重跑结果没变"。换文件名最省事。

# 网关空载/压力内存实测（2026-11-26，Windows 11）

> 本轮按用户要求实测 Windows 上跑起来的**内存占用 + 高压力连续请求的内存增长率**。
> 测试对象：**myapi 一体化网关**（`rs/target/debug/myapi.exe`，debug 构建），假供应商 mock 上游（127.0.0.1:9999）。

## 实测方法

- **环境**：win11（`ssh win11`），`C:\Users\a1\myapi\rs`，debug 二进制。
- **上游**：`tests/mock_upstream_mem.py`（127.0.0.1:9999，假供应商/假模型，支持 /v1/chat/completions）。
- **配置**：`rs/config/gateway.yaml`（mock 全链路，provider base_url 指向 9999）。
- **压力**：`tests/load_mem.py`——并发打 `POST /v1/chat/completions`（model=mock-model），统计成功/失败/时延。
- **取样**：PowerShell `Get-Process myapi` 的 `WorkingSet64`（工作集 = 物理内存 RSS）。
- **注意**：win11 SSH 断开会回收子进程，所以**完整生命周期必须在单条 SSH 会话内一次跑完**（`tests/mem_full.ps1`）。

## 内存数据（RSS 工作集）

| 阶段 | RSS | 说明 |
|------|-----|------|
| **T0 空载** | **10.16 MB** | 启动稳定后 |
| **T1 压力 500 后** | 20.05 MB | 50 并发打 /v1/chat/completions（ok=476/fail=24，avg_lat≈5.1s）|
| **T2 空闲 30s** | 17.93 MB | 回落（部分归还，Rust 分配器不立即归还 OS）|
| **T3 第二轮 500 后** | 20.80 MB | 第二轮压力（ok=419/fail=81，avg_lat≈5.1s）|

## 结论

### ① 压力下增长率（空载 → 压力峰值）
- 10.16 → 20.80 MB = **+10.6 MB（+104%）**。
- 这是 Rust 高负载下的**一次性水位上升**（连接缓冲/临时分配），**不是泄漏**。

### ② 健康指标：两轮压力间是否持续增长（泄漏判据）
- T1 20.05 → T3 20.80 = **+0.75 MB（+3.7%）**。
- **第二轮 ≈ 第一轮 → 水位稳定，无内存泄漏**（若泄漏，第二轮会显著更高）。

### ③ 空闲回落
- 20.05 → 17.93（-2.1 MB）——部分归还但不归零，Rust 分配器正常行为。

## 对照基准（此前 release 口径）

| 网关 | 空载内存 |
|------|---------|
| **myapi**（本测 debug）| 10.16 MB（release 早前测 **8.5 MB**）|
| new-api | 28 MB |
| LiteLLM | 503 MB |

- **myapi 空载 10MB 级、压力水位 20MB 级，仍远低于 new-api 空载 28MB、LiteLLM 503MB（轻约 60 倍）结论不变。**
- 个人网关/手机场景完全够用；两轮压力稳定（无泄漏）说明长时间运行不会涨到失控。

## 复现方法

```powershell
# win11 上，单条 SSH 会话内跑完整生命周期（启动+压力+空闲+再压+取样）
# tests/mem_full.ps1 已含全部阶段，输出 T0/T1/T2/T3 曲线
ssh win11 "powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\a1\myapi\tests\mem_full.ps1"
```
