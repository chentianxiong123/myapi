# 通道设计讨论：供应商的多种接入方式

> 状态：**设计讨论中，命名待最终拍板**（本文暂用「通道」，候选：通道 / 渠道 / 接入点）
>
> 背景：模型页重构成"健康度/熔断/路由/渠道来源"只读视图后，暴露出一个核心建模问题——
> **同一个供应商，内部往往有多种不同的接入方式**，现有数据结构装不下。本文记录讨论过程与结论。

---

## 一、要解决的三个刁钻场景

实测/实际需求中，同一个供应商内部需要区分多种接入方式，每种方式 = 一套 **key + 网络路径 + 上游模型名映射** 的整体：

| 场景 | 变的是什么 | 举例 |
|---|---|---|
| **① 模型名映射统一** | 上游模型名（同供应商、同 key、映射不同） | `deepseek-v4-flash` 这个对外名，要同时接住上游的大写 `DeepSeek-V4` 和小写 `v4.1`，调用方不用切换 |
| **② 多网络路径** | 网络路径（同供应商、路径不同） | 一个 websearch 模型：一条路走 IPv4、一条走 IPv4带key、一条走 IPv6 |
| **③ 多档位 key** | key 档位 + 覆盖范围（同供应商、key 不同） | 一个上游有 VIP key 和普通 key，各自覆盖的模型不一样 |

**共同本质**：三个都是「同一个供应商，内部有多种不同的**接入方式**」。
每一种方式 = **key × 网络路径 × 模型名映射** 三件套，绑死成一条。

---

## 二、现有数据结构装不下

当前 `Provider`（供应商）的结构（`web/src/lib/types.ts`）：

```ts
interface Provider {
  name: string
  base_url: string
  keys: Array<{ 'api-key': string }>   // ← 一堆 key 轮询
  models: Array<{ name, alias?, protocol?, kind? }>  // ← 模型名映射，但是 Provider 级共享
  proxy: string                         // ← 一个代理，Provider 级
  proxy_pool_id, proxy_strategy
}
```

问题：
- `keys` 是「一堆 key 轮询」，但 key 和「走哪条网络路径」「映射哪些模型名」是**绑死**的——现在拆不开。
- `models`（映射）、`proxy`（路径）都是 **Provider 级共享**，没法让「这个 key 走 IPv6 + 只映射这几个模型名」。
- 三个刁钻场景都要求 key + 路径 + 映射**作为一个整体**独立出来。

---

## 三、其他系统的"通道"定义对比

查了参考项目，各家都有一个"上游接入单元"的概念，但粒度和语义不同：

### new-api — 渠道（Channel）
- **定义**：一个渠道 = 一个上游供应商 + 一个 key（`base_url` + `key` + 模型列表）
- **粒度**：**渠道 ≈ 供应商**（扁平，渠道本身是顶层）
- **多 key**：渠道内 `keys[]` 轮询（和我们现在 Provider.keys 一样）
- **健康度**：**定时主动测试**（`auto_test_channel_enabled`，默认每 10 分钟测一次）
  - 测试模式：`scheduled_all`（定时全测）/ `auto_ban_only`（只自动封禁）/ `passive_recovery`（被动恢复）
  - 错误率高 → `ChannelStatusAutoDisabled`（自动禁用）+ 通知
- **跟我们不一样**：new-api 渠道 = 供应商（1:1）；我们要**供应商内部再分多个通道**（1:N）

### LiteLLM — Deployment（部署）
- **定义**：一个 deployment = `{model_name, litellm_params: {model, api_base, api_key, ...}, weight, priority}`
- **粒度**：**deployment = 一次完整接入配置**（key + base + 模型映射 + 权重，绑死）
- **路由**：Router 按 `model_name`（对外别名）聚合多个 deployment，按权重/延迟/优先级分流
- **健康度**：cooldown（429/超时 → 指数退避冷却）+ `health_state_cache` + 延迟感知（TTFT 滑动窗口）
- **最接近我们要的**：deployment 就是"key×base×映射 三件套"

### 9router — providerSpecificData + combo
- **定义**：`providerSpecificData`（每个 provider 的 key/proxyPoolId/connectionProxy）
- **多接入**：`pickProxyPoolId`（round-robin/random/none 轮换）；combo 模式多 provider 链式 fallback
- **健康度**：429 → 指数退避 cooldown（`base * 2^level`）；按额度冷却
- **跟我们不一样**：9router 的接入配置挂在 provider 上，没有"供应商内部多通道"的显式分层

### cc-switch — Provider + EndpointSpeedTest
- **定义**：Provider 卡片，`keys[]` 轮询
- **健康度**：`EndpointSpeedTest` 组件，在 provider 卡片里手动测端点速度
- **最简单**：没有独立的多通道分层

### 对比小结

| 系统 | 上游接入单元 | 粒度 | key×路径×映射 | 健康度 |
|---|---|---|---|---|
| new-api | 渠道 Channel | 渠道≈供应商（1:1）| 部分（key 独立，映射/路径共享）| **主动定时测** |
| LiteLLM | Deployment | = 一次接入配置 | **全绑死**（最像我们要的）| 被动 cooldown + 延迟感知 |
| 9router | providerSpecificData | 挂在 provider 上 | 部分 | 被动 cooldown |
| cc-switch | Provider | Provider（1:1）| 部分 | 手动测速 |
| **myapi（目标）** | **通道** | **供应商的子层（1:N）** | **全绑死** | **被动统计** |

## 四、我们的差异（跟它们都不一样的地方）

1. **通道是供应商的子层（1:N）**：
   - new-api / cc-switch：渠道/Provider ≈ 供应商（1:1）
   - **我们**：一个供应商 → **多条通道**（每条 = key×路径×映射）
   - 这是我们的核心差异，也是三个刁钻场景逼出来的

2. **健康度 = 被动，不主动探测**：
   - new-api：定时主动测试（用户明确不要）
   - **我们**：被动统计**真实请求**的成败/延迟/429 → 攒成健康度（像 LiteLLM cooldown）
   - 用户原话：「不是后端定时测，而是被动」

3. **熔断按通道粒度**：
   - 某条通道（某 key/某路径）挂了 → 只熔那条通道，不熔整个供应商
   - 其他通道照常服务

## 五、目标数据结构（草案）

```
Provider（供应商）                     ← 上游是谁（SenseNova / pie-xian）
  base_url: string
  ├─ 通道①：{ key: vip,   路径: IPv4,  映射: {DeepSeek-V4 → deepseek}, 健康: ... }
  ├─ 通道②：{ key: 普通,  路径: IPv6,  映射: {v4.1 → deepseek},        健康: ... }
  └─ 通道③：{ key: 无,    路径: IPv6,  映射: {...},                    健康: ... }

模型（alias，对外统一名）              ← deepseek-v4-flash
  └─ 分流到：通道①（weight 80%）+ 通道②（weight 20%）
```

- **供应商（Provider）**：上游是谁，base_url
- **通道（Channel，命名待定）**：供应商的一条具体连接 = key × 网络路径 × 模型名映射 三件套 ← 新增层
- **模型（alias）**：对外统一名，按权重分流到多个通道
- **熔断/健康度**：按**通道**粒度（被动统计）

## 六、命名讨论（待拍板）

候选名字（英文都是 channel / endpoint）：

| 名字 | 语义倾向 | 优 | 劣 |
|---|---|---|---|
| **通道** | 一条固定的数据通路 | 技术感、项目里已习惯（cpa 通道/iamhc 通道）| — |
| **渠道** | 供货/分发渠道 | new-api 用这个词，术语一致 | 商业感偏重 |
| 接入点（Endpoint） | 一个接入位置 | 中性、精确 | 生硬 |

**最终拍板：通道**（不再纠结）。
- 项目排查时一直用"通道"（cpa 通道、iamhc 通道），已形成肌肉记忆
- 比"路由"好（不会跟"请求分流 routing"混淆）
- **比"渠道"好（关键）**：new-api 语义里"渠道"≈供应商本身（渠道 = base_url + key + 模型，1:1）。
  若我们用"渠道"称呼这个**子层**，new-api 用户会误以为是**供应商**那一层——同一个词指两个层级，必乱。
  "通道"无此包袋，指"一条端到端通路"清晰。
- （"接入点/Endpoint" 中性但生硬，不如"通道"顺口）

**已定**：全局用「通道」（代码 Channel）。

## 七、连带决策（待确认）

1. **`Provider.keys`（多 key 轮询）废掉**：改成**一个通道挂一个 key**。要多种 key → 建多条通道。这样 key 和路径、映射永远绑死，不会乱。
2. **模型页删掉所有配置编辑**：模型页 = 只读运行态视图（健康度/熔断/路由分流/通道来源）。所有配置（建通道、配 key/路径/映射/权重）挪到**供应商页**。
3. **供应商页** = 配置中心（建供应商、建通道、配 key/路径/映射/权重）。
4. **模型页** = 健康度监控台（被动数据）：
   - 每个模型：状态灯（正常/熔断/异常）、成功率、实测 TTFT、请求数
   - 当前路由分流（通道①80% / 通道②20%，实际命中比）
   - 通道来源：这个模型由哪些通道供，各通道健康/权重/命中数
   - 熔断状态：哪条通道熔了、剩余时间
